# 澎湃 OS（HyperOS）收不到短信：原因与对策

## 用户现象（2026-10-14）

HyperOS 3 手机上鸿枢收不到新短信；设置页“系统广播到达”为 **0 次**，即 `SmsReceiver.onReceive`
从未被系统调用过（计数在任何开关判断之前写入）。用户随后开启了“自启动”与“通知类短信”。
本机无 adb 设备，以下厂商机制来自公开资料与社区复现，仍需按文末矩阵真机确认。

## 原因

鸿枢的 Manifest、BROADCAST_SMS 发送方保护与 PDU 解析符合 AOSP 要求，广播 0 次不是解析问题。
小米在运行时权限之外有私有 AppOps（非公开 SDK 常量，社区整理值）：

| 代码 | 名称 | 未允许时的影响 |
| --- | --- | --- |
| 10008 | `OP_AUTO_START` 自启动 | 进程不在时，系统不为 SMS_RECEIVED 拉起鸿枢；HyperOS 很快回收后台进程，等同于广播永不到达 |
| 10007 | `OP_BOOT_COMPLETED` 开机启动 | 开机广播不投递，周期任务与实时连接无法在重启后恢复 |
| 10018 | `OP_READ_NOTIFICATION_SMS` 通知类短信 | 106/955xx 等服务号短信（验证码、银行、运营商）不进入广播，**同时**从收件箱查询中隐藏，补漏也读不到 |

这些授权未允许时，标准 RECEIVE_SMS/READ_SMS 及其 AppOps 仍显示“已授予 · 系统策略允许”，旧诊断因此
给出误导结论（与 SmsForwarder [#509](https://github.com/pppscn/SmsForwarder/issues/509)“权限全绿也读不到”一致）。

另外，“免费网络短信”（小米互联网短信）、“5G 消息”/RCS 走 IP 通道，不产生 SMS_RECEIVED，也不一定写入
Telephony 收件箱；社区复现关闭二者后恢复接收。

应用自身的缺口：新安装默认关闭历史与新短信补漏；广播缺失时没有任何不依赖广播的即时路径。

不是原因：Android 17 起的 OTP 三小时扣留（HyperOS 3 基于 Android 16）；Android 15 的通知 OTP
脱敏（只影响通知监听，见下文风险）。

## 本轮对策

1. **厂商授权诊断**：识别小米/Redmi/POCO，经 `getprop` 读 HyperOS/MIUI 版本，反射
   `AppOpsManager.checkOpNoThrow(int,int,String)` 读取本应用 10008/10018/10007 状态；读不到时显示
   “无法读取，请人工确认”，从不推断为已允许。标准权限摘要在小米设备上改为指向厂商授权。
2. **一键跳转**：自启动管理页、安全中心权限编辑页（`com.miui.securitycenter` 多个历史类名），
   全部失败时回退到公开的应用详情页。页面说明省电策略“无限制”、关闭免费网络短信与 5G 消息。
3. **补漏建议**：小米设备上提供“开启新短信补漏（澎湃 OS 推荐）”按钮，仍是用户主动开启，不偷偷开启。
4. **收件箱即时补漏**：进程存活时对 `content://sms` 注册 ContentObserver（需 READ_SMS），变化后 3 秒防抖
   触发既有维护任务；只在新短信补漏或历史读取开启时扫描。不依赖广播，覆盖“广播被扣但收件箱可读”。
5. **短信通知兜底（用户 2026-10-14 明确要求，取代旧文档“不新增通知监听”的默认约束）**：
   可选 `NotificationListenerService`，默认关闭；开启时记录同意时间，只采集此后短信应用
   （`com.android.mms` 等及系统默认短信应用）发布的通知。MessagingStyle 中自己的回复、分组摘要、
   “N 条新信息”类汇总不采集。监听服务被系统绑定期间进程通常保持存活，广播路径也因此较少依赖自启动拉起（不作保证）。

### 通知分类（2026-10-18 真机误采修复）

真机上出现两类误采：系统为小米短信前台服务发出的占位通知（标题“短信正在运行”、正文“点按即可了解详情或停止应用”，
包名仍是 `com.android.mms`，且未带常驻标记），以及同一号码连发多条时的折叠通知（正文“[3条]【…】最新一条”）。
前者被当成发件人为“短信正在运行”的短信；后者只留下带前缀的最后一条，其余两条在通知中从未出现，且前缀使正文
无法与收件箱原文关联。

通知现在先分类，只有“消息”类才可能落库：

- **忽略**：非短信应用；常驻、`FLAG_FOREGROUND_SERVICE`；类别属于 service/sys/status/progress/err/call 等非消息类别
  （缺失类别允许）；标题以“正在运行 / is running”结尾或正文以“点按即可了解详情 / Tap for more information”开头。
- **汇总**：分组摘要；“N 条新信息”；正文开头或标题首尾带方括号/圆括号计数（`[3条]`、`(3条)`、`（2条新信息）`、
  `(3 messages)`）。汇总通知的文字不是任何一条短信，不落库；收件箱补读负责逐条取回（见下节调度）。`【品牌】`
  签名与正文中的普通数字不算计数。
- **消息**：其余短信应用通知，按下文身份规则处理。

### 通知只作信号，收件箱是逐条依据

- 开启“从通知读取”时同时申请 READ_SMS，并在本次同意内一次性开启“漏收检查”（新短信补漏）；用户此后单独关闭
  漏收检查不会被重新打开。此前已开启通知兜底的安装在下一次采集维护时同样联动一次。关闭通知兜底会清除联动记录。
- 短信应用的“消息”与“汇总”通知都会立即触发一次收件箱补读。广播、收件箱观察者与通知都只通过同一个采集入口
  （`requestCapture`）请求一次合并的采集轮次：补读收件箱 → 关联通知 → 上传；各来源不再各自调度任务。
- 通知落库的记录在与广播/收件箱记录关联前暂缓上传：号码标题 30 秒，名称标题 150 秒。放行前约 8 秒由独立定时任务
  再补读一次收件箱，覆盖先发通知后写收件箱的实现。关联成功的记录立即放行，并采用对端的号码、SIM 与时间。
- 暂缓期满仍未关联的通知记录才按原规则上传（仍需可靠接收号码），对应 RCS/免费网络短信等不进收件箱的消息。
  代价：这类只存在于通知中的验证码最多晚 30 秒上传。

数据库 v12 升级时一次性清理旧版已入队、尚未上传、也未与广播/收件箱关联的上述两类通知记录及其通知身份；
已与广播或收件箱关联的记录说明它确是短信，保留不动。已上传到中枢的旧记录不在本机清理范围。

### 通知兜底的去重与身份

- 通知只含会话标题（常为联系人名称）和正文，没有订阅 ID。标题是号码时规范化为号码；有通讯录权限且
  名称唯一对应一个号码时还原为号码，否则保留名称。
- 同源幂等与跨源关联分开：MessagingStyle 的身份由包名、通知 key（仅作容器）、原始发件人、正文、消息自身时间和相同元组的出现序号组成。不同消息时间的连续相同正文各自保留；通知 postTime/when 改变、行顺序改变不影响已识别消息，完整快照重放新增 0 条。身份在联系人解析前生成，不依赖稍后补全的号码。
- 普通通知没有结构化消息时间，按标题、正文、可用通知时间及容器识别完全相同的观察；时间变化无法证明是重发还是新短信，保留独立记录并标注“不确定”。结构化消息的完全相同元组也保留出现次数并标注不确定；ROM 若把不同短信的全部可见字段都复用，客户端无法恢复其真实数量，不承诺从不可区分的观察推导消息身份。
- ±2 分钟窗口仅用于通知与广播/provider 的跨源关联，必须有发件人证据、SIM 兼容且双方候选唯一，一条对端只能关联一条通知身份。整批结构化消息先保存再匹配，不能按遍历次序吞掉连续重复正文。无法唯一关联时保留队列并显示“不确定”，不按最近时间猜测。
- 通知先到且唯一关联成立时，把通知行升级为精确发件人、订阅与接收号码（仍未上传时生效）。通知后到时持久记录对端关联；通知身份与关联均在 ACK 后、数据库重开后保留，重放新增 0 条。
- 通知 key 改变或升级前 legacy 证据与新结构化身份无法对应时，保留独立观察并标记身份不确定，不凭相同正文跨 SIM 合并。
- 多个通知身份可能对应同一上传指纹（receiver/sender/消息时间/正文）；协议无法表示这种次数差异。首个 canonical capture 占用该指纹，其余进入持久“通知身份碰撞，需处理”状态，不能通过 duplicate ACK 或同步下载自动清除。批内、跨批、ACK 后与重开均保留占用证据；号码/发件人补全后按实际上传指纹重新检查。可核实接收号码并更正，或由用户明确放弃；普通“重试”不解除碰撞。已确认一对一的跨源副本共用 canonical capture，不被当成独立身份碰撞。
- 无订阅 ID 的通知行与旧补漏行一样，只在用户确认单卡时使用单卡兜底；双卡时显示“接收号码待确认”，等待广播/补漏校正。
- 不记录、不导出通知正文到日志或诊断；只计数短信应用通知到达次数与时间。
- 诊断页“采集事件”（SQLite v13 `capture_events`，最多 200 条，同来源同结果 60 秒内合并计数）只记录时间、来源
  （系统广播/短信通知/漏收检查/历史补齐）与结果代码：广播已保存/重复；通知已忽略（系统或服务通知）、汇总已请求补读、
  暂存 N 条、已与收件箱/广播关联、补读后关联、未找到对应短信按通知上传；收件箱新增 N 条。不含发件人、号码或正文，
  随“复制诊断信息”一并导出，用于在真机上判断每条短信走了哪条路径。

### 已知风险

- 系统设置中授予“通知使用权”对旁加载应用可能先要求在应用信息右上角“允许受限设置”（Android 13+）。
- Android 15+ 若设备启用了敏感通知脱敏，验证码正文可能被替换；国行 HyperOS 是否启用需实测。
- 不同版本小米短信的通知字段（标题格式、是否 MessagingStyle）未经完整真机确认；已知 HyperOS 对同号码多条使用
  “[N条]”折叠普通通知，因此通知路径无法逐条还原，必须依赖收件箱补读。
- 正文恰好以“点按即可了解详情”开头的真实短信会被通知路径忽略（广播/收件箱路径不受影响）。
- 未来 Android 17 对 OTP 的三小时扣留会同时作用于广播与收件箱查询（官方页面对 target SDK 的描述不一致），
  届时广播/补漏路径的验证码可能延迟，通知兜底是否受影响需重新评估。

## 真机验收矩阵

记录机型、HyperOS/Android 版本、鸿枢版本、单/双卡，保持小米短信为默认应用，使用合成正文。

1. 升级后打开“同步控制”，记录“厂商短信授权”三项状态；若显示“无法读取”，按按钮进入系统页人工确认。
2. 自启动、通知类短信、省电无限制全部开启；关闭免费网络短信与 5G 消息。退到后台，另一台手机发普通短信：
   广播次数应增加，本机待同步页出现记录。
3. 再发 106 验证码类短信，对照广播次数；不增加时开启新短信补漏，确认补漏能否读到。
4. 开启短信通知兜底并授予通知使用权，再发验证码：本机待同步应只出现一条；若广播也到达，记录应升级为号码发件人。
5. 双卡分别接收，确认通知行等待号码确认或被广播/补漏校正，不按卡槽猜测。
6. 重启手机并解锁后重复 2–4。
7. 同一号码一分钟内连发三条不同合成正文（复现“[3条]”折叠）：待同步/中枢应出现三条独立短信、发件人为号码，
   采集事件应依次出现“多条折叠的汇总通知，已请求补读收件箱”与“从收件箱新增 3 条”，不出现“[3条]”开头的记录。
8. 触发小米短信的前台服务（如发送彩信或大批量导入时），确认“短信正在运行”类通知只在采集事件中显示为
   “系统或服务通知，已忽略”，不进入待同步列表。
9. 在关闭广播、补漏可读的情况下发验证码：采集事件应出现“暂存 1 条”随后“已与收件箱记录关联”，30 秒内上传，
   中枢只有一条且发件人为号码。若出现“未找到对应短信，按通知内容上传”，记录对应的 ROM 版本与正文长度
   （是否被通知截断），这是通知与收件箱正文不一致的信号。
10. 同一发件人在两分钟内连续发送两条相同合成正文，确认结构化通知中两条消息均保留；重发同一快照、
   仅更新通知容器时间、ACK 后重新绑定监听均不新增。双卡/多候选无法唯一关联时应保留副本并显示
   “通知身份或跨源关联不确定，已保留”，不得把两条消息压成一条。普通通知时间改变的情况按独立不确定观察验收。
