# 后台收不到验证码：分析与修复

> 2026-10-18 起，诊断页“采集事件”按时间列出每个来源（系统广播、短信通知、漏收检查、历史补齐）的处理结果，
> 不含短信内容；排查“收不到/重复/少条”时先复制诊断信息，对照 [HYPEROS_SMS.md](HYPEROS_SMS.md) 的验收矩阵。

## 用户现象与结论边界

用户实际观察：鸿枢在后台时验证码未同步；重新进入后“本机待同步短信”为空。
厂商短信与 Google Messages 分别作为默认应用时都能复现。
目前未提供机型、ROM/Android 版本、普通短信对照、实际授权状态或广播入口计数；本机
`adb devices -l` 没有设备，不能把某一厂商策略认定为已经在用户手机上验证的根因。

队列为空只说明当前没有未 ACK 的 outbox 行，不等于已经证明 READ_SMS 不可用。
缺失 SIM 映射、离线或中枢拒绝上传不会主动删除捕获的短信，这些情况下应仍有待同步行。
成功 ACK 会删除待同步行，但应能在中枢的已同步收件箱看到短信。

## 确定的应用缺陷

1. **广播缺失时没有默认恢复路径。** `AccountSheet.kt` 的实时开关仅请求 RECEIVE_SMS；
   新安装的 `Config.historyEnabled` 为 false。`MainActivity.onResume → syncNow → CaptureWorker`
   调用的 `catchUpInbox` 在历史关闭时直接返回，不访问系统收件箱。因此“未投递广播 →
   outbox 为空 → 重新进入仍不补扫”是原实现的确定行为。若用户已经开启历史并实际授予
   READ_SMS，则还需检查查询结果/系统策略，不能用这个条件分支单独解释其真机故障。
2. **广播生命周期结束早于持久任务入队。** 原 `SmsReceiver` 调用返回 Job 的 `syncNow` 后
   立即 `pending.finish()`。异步协程尚未写入 WorkManager 时进程即可被回收；本地短信
   已保存但即时同步触发可能丢失。此缺陷单独不会导致 outbox 为空。
3. **运行中的任务吞掉新触发。** 原 `syncNow` 只要存在未完成同步就返回。若新短信在该
   worker 读取最后一批后入队，就没有后继同步，只能等待其他事件/周期任务。旧维护任务
   的 KEEP 也可能吞掉扫描结束后的新授权/新短信触发。这些缺陷造成延迟，不等于广播未收到。
4. **诊断不足。** SQLite 的“广播次数”原来随成功入库事务提交，解析/存储失败时不能
   表示入口是否收到；网络成功与权限 granted 也不能证明广播/验证码可达或收件箱可读。
   原历史查询空结果仍提示“短信读取正常”，容易误导。

## 系统侧假设：需真机区分

- Android 的 SMS_RECEIVED 不要求鸿枢持有默认短信角色；Manifest 已声明接收权限、
  exported receiver、BROADCAST_SMS 发送方保护及正确 action，无证据表明这里拼写错误。
- 官方 [SMS_RECEIVED_ACTION 文档](https://developer.android.com/reference/android/provider/Telephony.Sms.Intents#SMS_RECEIVED_ACTION)
  明确说明，带 SMS Retriever 哈希的短信可能只向对应应用和指定列表投递。
- 厂商可能另设通知类短信、验证码读取、后台/自启动等策略；运行时权限 granted 不等于
  AppOps 放行，也不等于厂商放行敏感短信。更换默认短信应用不会更改鸿枢的这些权限。
- Android 15 的 [OTP 通知脱敏](https://developer.android.com/about/versions/15/behavior-changes-all#otp-redaction)
  针对 NotificationListenerService，不能据此直接认定 SMS 广播被拦。
- RCS/MMS、已被删除或仅存在其他应用私有库的消息不属于 Telephony SMS 收件箱补漏范围。

## 本轮修复

- 默认仍保持实时/历史分离。新增用户主动开启的“新短信补漏”，独立请求 READ_SMS；
  只读取开启时间之后的系统收件箱，不偷偷打开全量历史。总采集关闭后重新开启，重新
  建立时间边界；关闭期间的消息不按新短信导入。开启前遗漏的消息使用已有历史补齐功能。
- 补漏与历史采用独立 provider ID 水位，共用持久去重账本和 ACK；补漏不会使未来历史
  扫描跳过旧短信，不改服务端 API/schema、版本号或既有队列。
- 广播 goAsync 完成前等待 WorkManager 持久入队；存储失败与调度失败分别展示。
  同步/维护运行时允许最多一个后继，已有离线/退避/后继任务继续合并，不密集重建任务。
- 系统广播入口次数/时间独立持久记录；显示 RECEIVE_SMS/READ_SMS 与标准 AppOps 策略。
  增加“立即读取并检查收件箱”。查询新增 0 条不再宣称“读取正常”或“没有短信”。
- 不申请默认短信角色、发送短信权限、特权权限或通过私有 URI 绕过保护。
- 后续（2026-10-14）：澎湃 OS 真机广播计数为 0，定位为厂商自启动/通知类短信授权；按用户要求新增默认关闭的
  短信通知兜底与收件箱即时补漏，见 [HYPEROS_SMS.md](HYPEROS_SMS.md)。
  诊断不输出真实短信、号码、验证码、PDU 或异常原文。

## 真机最小复现矩阵

记录机型、ROM/Android 版本、鸿枢版本、总同步/历史/新短信补漏开关。
不要卸载、清数据或删除既有待同步队列来“重试”。

1. 打开“实时广播与同步”，确认实际接收/读取权限及访问策略，记录广播入口计数。
2. 保持原默认短信应用，退到后台，用另一台手机发一条合成普通文字短信，再测试验证码。
   对照广播计数是否分别增加，而不只看中枢网络连接。
3. 开启新短信补漏并授权 READ_SMS，**再接收一条新短信**。短暂断网，重新进入并点
   “立即读取并检查收件箱”，记录新增条数与本机待同步行。补漏不读取开关开启前的短信。
4. 恢复网络，检查 ACK 后待同步行消失且中枢出现同一条短信；双卡分别验证准确归属。
5. 若普通短信广播增加而验证码不增加，但 provider 能补到验证码，定位为该消息广播
   路径受限且补漏有效；如果普通短信也不增加，检查 RECEIVE_SMS/AppOps/后台、自启动。
6. 若默认应用可见而历史/新短信补漏均查不到对应 SMS，则记录系统查询/访问策略和
   消息类型，排查厂商隐藏、验证码访问策略或私有/RCS 存储；不能靠改上传逻辑解决。
7. 若广播增加且显示解析/存储失败，按固定错误类别定位应用捕获路径；若本地存在而
   中枢没有，转查 SIM 配置、授权、网络与 ACK，不再归因于短信读取。

宿主合成 PDU、原生 SQLite、权限与调度合同可证明应用逻辑，不证明运营商真实广播、
厂商策略或手机重启/长时后台已经通过。验证命令与实际结果见 [VALIDATION.md](VALIDATION.md)。
